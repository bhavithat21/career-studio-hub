# Cloud database setup order

Use the Node version in package.json (Node 22.15 or newer) and the committed lockfile. Install the project's pinned dependencies before running these scripts. Keep the database private, use the provider's TLS connection settings, and store all environment values in the deployment's server-side secret configuration. Do not paste credentials into command arguments or output files.

1. Provision a PostgreSQL database and private Vercel Blob store. Set DATABASE_URL and private Blob access configuration securely. Take a database backup before changing an existing schema.
2. Set BETTER_AUTH_SECRET to a stable random secret of at least 32 characters. Set BETTER_AUTH_URL to the canonical HTTPS site origin, plus GOOGLE_CLIENT_ID and GOOGLE_CLIENT_SECRET. Register that origin's `/api/auth/callback/google` with the Google OAuth client. Keep basic login separate from optional Gmail authorization.
3. Inspect the Better Auth schema plan with `node scripts/migrate-auth.mjs`. This default mode connects only to inspect the schema and prints table/column/index names and conflict counts, without secret values or account records.
4. Review the plan, then explicitly run `node scripts/migrate-auth.mjs --apply`. This uses the installed Better Auth version's migration API with the application's actual auth configuration. Unsafe additions and schema conflicts block execution. Migration statements may execute sequentially; retain the backup in case a provider failure leaves a partial migration, then rerun the plan before retrying.
5. Apply `db/tenant-records.sql` with the provider's secured SQL console or approved migration tooling. Business records use `(tenant_id,key)` as the primary key and retain the JSON payload as TEXT. Do not copy a single-user database into an unscoped global table.
6. Deploy, verify Google login for two different users, and confirm their workspaces and PDFs remain isolated. New users must start without another candidate's profile, resume, jobs or mail. Configure the scheduler with a separate CRON_SECRET; never treat a request-supplied user ID as authentication.
7. Migrate historical records and private PDFs only into the owner's verified Better Auth user ID, preserving original IDs, exact JSON strings and PDF bytes. Exclude temporary locks. Freeze the old scheduler and writes before final cutover, verify counts and hashes, and keep the original private service available for rollback until validation is complete.

No migration or provider request runs as part of the Next.js build. `--help` does not access the database. This setup script does not import candidate data or deploy the application.

Production Secret values cannot be pulled back from Vercel. To derive and migrate only the schema, use `node --env-file=.env.production.local scripts/migrate-auth.mjs --schema-only` after the ignored environment file has DATABASE_URL. This mode supplies a process-local ephemeral auth secret and dummy Google fields with the real canonical base URL, using the same app options without signing in or calling Google. It does not modify remote environment values. Review the read-only plan before adding `--apply`; this schema-only mode is never a deployed auth configuration.
