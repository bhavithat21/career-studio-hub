## Runtime and server setup

Deploy this folder as a native Next.js project on Node 22 with the committed package lock. `vercel.json` uses `npm ci`, `npm run build`, a 300-second API limit, and one daily maintenance cron. Confirm Fluid Compute is enabled for the 300-second limit; no plan upgrade or purchase is configured here. Configure PostgreSQL, a **private** Vercel Blob store, Google OAuth and the stable canonical HTTPS origin before enabling users. Schema order is in [scripts/HUB-DATABASE-SETUP.md](scripts/HUB-DATABASE-SETUP.md).

Server-only environment names: `DATABASE_URL`, `BLOB_READ_WRITE_TOKEN` (or supported Blob store/OIDC configuration), `BETTER_AUTH_SECRET` (stable, random, at least 32 characters), `BETTER_AUTH_URL`, `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, and a separate random `CRON_SECRET` of at least 24 characters. Optional resume AI uses `OPENAI_API_KEY` and `ANTHROPIC_API_KEY`; quota configuration is `AI_DAILY_LIMIT`. Never put these values in `NEXT_PUBLIC_` variables, source, browser responses or build artifacts.

Vercel Cron sends `GET /api/maintenance` with its bearer secret. The route also supports authenticated per-user maintenance; only an exact cron secret permits global enumeration. The configured schedule is daily at 15:15 UTC. Hobby cron invocation can vary within the scheduled hour. Each cron run selects up to three users, prioritizes saved unfinished discovery runs while reserving a slot for the oldest unserved profile, and queues each selected user’s full enabled-source list. Requested progress, per-source results, attempts and worker leases are persisted in PostgreSQL. Vercel Queues processes one saved source dispatch per private consumer invocation, using managed at-least-once delivery, idempotent dispatch keys, delayed retry messages and a five-delivery platform cap. Signed queue envelopes bind each tenant and saved dispatch. Managed trigger delivery is private; on the current production deployment, the consumer HTTP URL returned 404 for a forged CloudEvent. The source route additionally rejects unauthenticated calls before the SDK can make broker requests, providing a fail-closed guard if a future routing configuration exposes it. The route accepts only bounded inline-v2 JSON with a valid server HMAC; legacy and routing-only callbacks fail closed. Producers enforce envelopes smaller than 4 KB. Publishing is awaited before acknowledgment, and duplicate delivery does not repeat a completed source dispatch. Recursive HTTP self-invocation has been removed because it is subject to platform recursion protection. Failed, expired or exhausted deliveries remain resumable through the UI or daily cron. Retry windows and exhausted attempts stay visible; access blocks are not bypassed. It does not promise every portal or user is refreshed daily. The configuration does not enable hourly execution. The exact Queue consumer entry must precede the broad API glob in vercel.json: the installed Vercel builder selects the first matching function pattern, so reversing these entries silently masks the trigger. Queue authentication is automatic via deployment OIDC; no local production credential export is required. Vercel currently includes the first 1,000,000 Queue API operations on Hobby, with normal Functions compute limits still applying; no plan upgrade or new paid subscription was made. [Queue pricing](https://vercel.com/docs/queues/pricing) and [private consumer setup](https://vercel.com/docs/queues/quickstart). [Vercel cron limits](https://vercel.com/docs/cron-jobs/usage-and-pricing) and [function duration](https://vercel.com/docs/functions/configuring-functions/duration).

Initial database setup has completed. `scripts/build-hub.mjs` permits initialization only when `HUB_INITIALIZE_DATABASE=1` is supplied for a reviewed one-time production build. It requires the exact project ID and server DATABASE_URL, holds a transaction-scoped advisory lock, refuses existing non-system tables/views/sequences, checks the read-only plan, then applies only expected fresh auth tables and the tenant table. Schema derivation uses in-memory placeholder OAuth fields and a temporary auth key, without Google requests or credential export. Leave the flag absent on subsequent builds. Existing or partially initialized databases stop for operator review; this is not a general upgrade or repair path. The one-time database initialization does not expose a public database-management endpoint.
